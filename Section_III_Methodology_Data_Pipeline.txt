Section III: Methodology and Data Preparation Pipeline

This section describes the end-to-end methodology used in our study, with an emphasis on the data engineering decisions that enable reliable and reproducible vulnerability detection experiments. Our core goal is to compare and combine (i) graph-based learning over Code Property Graphs (CPGs) and (ii) transformer-based code semantics, while minimizing confounds caused by dataset leakage, inconsistent preprocessing, and schema drift across extraction tools. The result is a unified pipeline that transforms raw dataset splits into per-function C programs, extracts CPGs in GraphSON format, discovers and validates graph schemas, builds synchronized vocabularies for nodes and edges, generates cached embeddings using multiple encoders (including locally trained word2vec), and finally constructs PyTorch Geometric (PyG)-ready cache artifacts where discrete structural features and dense code embeddings are fused.

We first motivate why this pipeline is necessary by discussing practical limitations we observed in prior work and in commonly used datasets. We then describe each preprocessing stage, the artifacts produced, and how the stages remain aligned to avoid silent representation mismatch.

III-A. Why a Dedicated Data Pipeline is Necessary

Graph-based vulnerability detection is sensitive to both the structure of extracted graphs and the content signals attached to nodes and edges. Two implementations that nominally use the same dataset can yield materially different results when they diverge in: (1) how they split code into functions, (2) how they normalize or clean code text, (3) what graph schema is extracted (node labels, edge labels, property keys), and (4) how embeddings are computed and fused.

In our development process we encountered three recurring issues that motivate a robust and explicit data pipeline.

1) Performance degradation across datasets and extraction settings.

Many models that report strong results on a single benchmark degrade when applied to a new dataset or even to the same dataset processed with a different extraction configuration. This degradation is often attributed to domain shift, but in practice it can also be caused by representation shift: edge categories may be missing, node or edge properties may be ignored, or the mapping from raw GraphSON fields to model features may differ between runs. Without a strong alignment mechanism, it becomes difficult to interpret whether a performance change reflects the model or the preprocessing.

2) Data inconsistency and quality issues in function-level datasets.

Function-level vulnerability datasets typically originate from heterogeneous sources. Some functions are incomplete when extracted (missing surrounding type definitions, macros, or include context). Others contain non-compilable fragments, truncated bodies, or merged snippets. Labels may be noisy or inconsistent, especially when derived from commit metadata or weak heuristics. In Devign-like settings, it is also common to find duplicated or near-duplicated functions across splits, which can cause leakage and lead to optimistic validation metrics.

3) Hidden leakage through duplicates and split contamination.

A realistic evaluation must ensure that near-identical code does not appear across train/validation/test, especially in vulnerability detection where patterns can be memorized. Leakage is not always obvious because duplicates may differ in whitespace, comments, file paths, or minor edits. Therefore, split-aware deduplication must be based on the actual function source content after applying a consistent normalization procedure.

Our pipeline addresses these issues using explicit hashing, schema discovery, configuration versioning, cache signatures, and deterministic artifact generation.

III-B. Datasets and Experimental Scope

Our pipeline supports multiple function-level datasets with different provenance and labeling conventions. In our setup, Devign is used as a baseline reference dataset for comparison with prior work. We also incorporate additional datasets such as Reveal and Draper to evaluate robustness and generalization.

While the details of the dataset distributions are reported in the Experiments section, the key methodology point is that all datasets are converted into a unified representation:

- Each split is materialized as a directory of per-function C files (one function per file).
- Each split has a manifest CSV that records function_id, label(s), provenance metadata, and a content hash.
- Each split is processed by Joern to produce a per-function CPG and GraphSON exports.
- All subsequent stages (schema discovery, vocab building, embedding generation, and cache construction) operate on these standardized artifacts.

This conversion allows us to use the same model implementations and training code across datasets, and ensures that differences in results are more likely to reflect dataset content rather than preprocessing drift.

III-C. Data Integrity: Deduplication and Function Completeness

The first stage of preprocessing focuses on dataset hygiene. The objective is to (i) remove duplicates across splits using hashes derived from actual function content and (ii) filter or repair obviously malformed functions.

1) Content-based hashing (SHA-256).

We compute a SHA-256 hash over the normalized function source. The normalization includes:

- Canonicalizing line endings (CRLF -> LF).
- Removing trailing whitespace.
- Collapsing excessive blank lines.
- Optionally removing C/C++ comments while preserving string and character literals.

The key design choice is that hashing should reflect the semantics-carrying function text, not metadata such as file names or project names. Computing the hash after normalization ensures that duplicates are detected even when they differ in formatting or comments.

2) Split-aware deduplication.

In real-world deployment, a model is trained on historical code and evaluated on future or unseen code. Therefore, the correct deduplication policy is not global random removal, but split-aware removal that prevents identical functions from appearing across splits. Concretely, we prioritize keeping a function in the training split when a duplicate is found in validation or test, and we remove duplicates from the later splits to avoid leakage. The exact policy can be configured, but the essential property is that no hash is shared across splits after deduplication.

3) Function completeness and sanity checks.

Many per-function datasets contain fragments that are not valid standalone translation units. This is expected because per-function extraction loses surrounding includes and type definitions. However, some fragments are worse than others: completely empty bodies, truncated functions, or code that is not even syntactically recognizable as C/C++.

Our pipeline uses lightweight completeness checks during per-function materialization and during Joern parsing:

- Empty or near-empty functionSource is filtered.
- Line-ending normalization and optional comment stripping are applied.
- Joern parsing is performed in isolated environments with minimal header stubs to satisfy common types (size_t, uint32_t, NULL, memcpy, etc.).
- Per-function parse failures are logged and retried (and can be reprocessed with a forced language mode).

The pipeline is designed to keep as many functions as possible while ensuring that the graph extraction stage does not silently produce degenerate graphs.

III-D. Per-Function C File Generation and Manifests

After deduplication and basic cleaning, each dataset split is converted into per-function C source files and a manifest.

1) Per-function file layout.

For each split (train, validation, test), the pipeline creates a directory:

- <perfunc_base>/train/
- <perfunc_base>/validation/
- <perfunc_base>/test/

Inside each directory, functions are saved as:

- train_func_0000001.c
- train_func_0000002.c
- ...

This naming scheme is deterministic and stable across reruns when the same input ordering is used. Determinism is important because it simplifies traceability between input rows, output files, and downstream graphs.

2) Manifest schema.

For each split we generate a manifest CSV, typically named manifest_<split>.csv, with one row per function. Common columns include:

- function_id: the filename of the per-function C file.
- label: binary vulnerability label (0/1) for Devign/Reveal-style settings.
- project: optional provenance label for grouping and analysis.
- orig_index: original row index in the source CSV for traceability.
- hash: SHA-256 over normalized function text.
- size: a size statistic (characters or lines) to aid analysis.

For datasets with richer labels (e.g., Draper with CWE fields), we include additional columns such as CWE-119, CWE-120, etc., and a combined label field (e.g., combine) that is mapped to the binary label column used by the training pipeline.

The manifest is the contract between preprocessing and graph extraction. It allows us to reproduce any function and to associate exported graphs back to labels.

III-E. CPG Extraction with Joern and GraphSON Export

The next stage generates CPGs and GraphSON exports for each per-function file. We use Joern, a widely used CPG extraction framework in vulnerability research.

1) Per-function parsing strategy.

Per-function code lacks includes and compilation context. Instead of attempting to reconstruct a full project build, we parse each function in isolation. This has two benefits:

- Scalability: functions can be processed in parallel.
- Robustness: parse failures are localized; one failure does not halt the entire pipeline.

To reduce parse errors, the pipeline generates minimal header stubs in a temporary include directory when certain tokens are detected in the code (e.g., size_t implies a typedef stub; NULL implies a macro definition). This approach is intentionally conservative: it aims to satisfy common dependencies without overfitting to specific projects.

2) Language selection and retries.

Joern supports both C and C++ frontends. In mixed datasets, some functions include C++ constructs even when stored with a .c extension. The pipeline supports:

- A global forced language mode (force-language c or force-language cpp).
- Automatic inference based on file extension or simple keyword heuristics.
- A retry strategy that can fall back from cpp to c when a cpp parse fails (useful for stability).

3) Parallel execution and timeouts.

CPG extraction is CPU-intensive and can be executed in parallel using a process pool. We configure worker counts separately for parsing and exporting. Each function parse/export is protected by a timeout, and parse/export can be retried a small number of times. Logs are written per function to support debugging.

4) Outputs.

For each split, the pipeline writes:

- labels.json: mapping from function_id (stem) to label.
- projects.json: mapping from function_id to project name.
- <split>/<function>.cpg.bin: the CPG binary (optional; can be deleted after export).
- <split>/exports/<function>/export_all/export.json: GraphSON export of the full graph.

The GraphSON files serve as the stable data source for subsequent schema discovery and vocabulary building.

III-F. GraphSON Schema Discovery and Configuration

GraphSON exports encode nodes and edges with labels and property dictionaries. However, the schema is not always identical across datasets or Joern versions. For example, the set of edge labels may differ depending on overlays enabled, and some property keys may appear in one dataset but not another.

To prevent mismatch between extracted graphs and model assumptions, we perform schema discovery:

1) Node and edge type enumeration.

We scan representative exports and collect:

- Unique node labels (node types).
- Unique edge labels (edge types).
- Frequently used node and edge properties (e.g., code, name, fullName, lineNumber).

We compute counts and report the number of unique node types and edge types. These statistics help define the dimensionality of one-hot structural features and the mapping of edge labels to integer IDs.

2) Dataset-agnostic configuration.

Instead of hardcoding schema assumptions for one dataset, we maintain a configuration layer that can be reused across Devign, Reveal, and Draper. This configuration maps GraphSON labels/properties to the standardized fields used downstream. When differences are found (for example, a new edge label in Draper graphs), the configuration can be updated without rewriting the entire pipeline.

3) Signature and versioning.

Schema discovery outputs are stored as artifacts (e.g., discovery summaries and comparison reports). These outputs provide a provenance record and are also used in later stages to derive cache signatures. The objective is simple: if the graph schema changes, the cache signature must change, forcing regeneration of vocabularies and features rather than silently reusing incompatible artifacts.

III-G. Vocabulary Construction for Node Types, Edge Types, and Content

Graph learning requires converting symbolic graph attributes into numeric tensors. We use a two-part representation:

- Discrete structural features: node type IDs, edge type IDs, and optional one-hot encodings.
- Continuous semantic features: embeddings derived from node content and edge content text.

To enable both representations, we build synchronized vocabularies.

1) Node type and edge type vocabularies.

We map each unique node label and edge label to an integer ID. These mappings are stored as JSON vocab files.

This mapping serves multiple purposes:

- It defines the dimension of one-hot node type features.
- It defines the number of edge types used by edge-aware GNN layers.
- It provides a stable mapping across experiments.

2) Node content and edge content vocabularies.

Beyond node and edge labels, GraphSON nodes and edges include text properties. Typical examples include:

- Node code fragments (e.g., operator tokens, identifier names, literal values).
- Node fullName or method signatures.
- Edge properties indicating calls or dependency metadata.

A key design choice in our pipeline is to treat node content and edge content as separate corpora. This addresses a common limitation in earlier pipelines that only embed node content. Edge content can contain useful semantics, especially when edges encode call relations, parameter passing, or data dependencies.

3) Hashing content strings for synchronization.

To scale embedding generation and to ensure deterministic alignment between text and graph elements, we compute hashes for each unique content string and build a corpus file (strings_to_embed.csv). Each entry includes:

- kind: node_content or edge_content.
- content_hash: hash of the normalized string.
- text: the string to embed.

Hashing is crucial for synchronization. The same string may appear in many nodes/edges across many functions; embedding it once and caching the result improves efficiency. Furthermore, using hashes as keys avoids issues with encoding, quoting, and CSV parsing when strings contain commas or escape sequences.

4) Noise handling.

Real GraphSON exports contain strings that are unlikely to be helpful for learning, such as file-scoped placeholders (e.g., "<global>") or per-function file prefixes that leak split identifiers. Such strings can inflate the vocabulary and introduce spurious correlations. Our preprocessing includes filtering rules and normalization to reduce these artifacts, focusing the embedding corpus on semantically meaningful tokens.

5) Alignment with PyG.

The vocabulary stage is designed to match the downstream graph tensorization step. When a graph is converted to a PyG Data object, each node and edge must be assigned:

- A type ID (from the node/edge type vocab).
- Optionally, a content embedding (looked up by content hash).

By building the corpus and vocabularies directly from the GraphSON exports, we ensure that every content string referenced during tensorization has a corresponding entry in the embedding cache, avoiding missing-key errors and silent fallbacks.

III-H. Code Embedding Generation and Caching

Once the embedding corpus is prepared, we generate dense vector embeddings for each unique string. We support multiple embedding sources to explore the trade-offs between pretrained transformer semantics and lightweight local embeddings.

1) Supported embedding sources.

Our pipeline supports the following embedders:

- UniXcoder: strong general-purpose code representation, often used for code understanding tasks.
- GraphCodeBERT: pretrained to incorporate data flow signals, relevant for vulnerability patterns.
- CodeT5+: encoder-decoder family; typically strong in code generation and representation.
- Word2vec: locally trained on the dataset corpus, providing lightweight embeddings tailored to the dataset vocabulary.

2) Multi-extractor and SQLite caches.

Embeddings are computed by a multi-extractor module that reads strings_to_embed.csv and writes embeddings to an SQLite cache. Caching in SQLite provides:

- Fast key-value lookup by hash.
- Efficient incremental updates.
- Portability and easy inspection.

The cache is keyed by (kind, content_hash) so that node_content and edge_content embeddings can be stored separately even when the raw text overlaps.

3) Single word2vec for node and edge content.

For locally trained word2vec, we train a single embedding space on the combined corpus of node and edge content strings. This yields a consistent vector space where embeddings for node tokens and edge tokens are comparable and can be fused downstream. Training a single model is also operationally simpler than maintaining separate models.

We apply standard practices to improve stability:

- Tokenization consistent with the corpus normalization.
- Clipping extreme token values when necessary.
- Recording training statistics (vocabulary size, coverage, etc.).

4) Dimensionality and compression.

Transformer embeddings can be high-dimensional (e.g., 768). For efficiency and to match model capacity, we support compressing embeddings to lower dimensions (e.g., 256 or 128) using deterministic projection or learned compression. This allows fair comparison across embedding sources and reduces GPU memory usage.

III-I. Cache Manager: Building PyG-Ready Graph Datasets

The cache manager is responsible for converting GraphSON exports and embedding caches into training-ready artifacts. This stage bridges program analysis outputs and machine learning inputs.

1) Graph tensorization.

For each function graph, we construct:

- edge_index: adjacency representation.
- edge_type: integer edge type IDs.
- x: node feature matrix.
- y: label.

The node feature matrix x is constructed by fusing multiple feature components:

- One-hot node type features (optional).
- Structural features (optional), such as degree statistics or handcrafted vulnerability signals.
- Code embeddings for node content (optional).
- Code embeddings for edge content (optional; may be included via edge feature channels or aggregated into node features depending on fusion design).

2) Feature fusion and concatenation.

A central design decision is how to combine discrete structural encodings with dense semantic embeddings. In our pipeline, the default approach is early concatenation (early_concat), where features are concatenated along the feature dimension:

x = [one_hot(node_type) || embed(node_content) || embed(edge_content_agg) || structural_features]

Here, || denotes concatenation. This approach is simple, preserves information, and allows the downstream GNN to learn how to weight each component.

Concatenation also requires strict dimensional bookkeeping. The cache manager computes the expected input dimension as the sum of enabled components and validates that the resulting tensors match this expectation. This validation prevents a common class of bugs where embedding dimensions and one-hot dimensions become inconsistent with model hyperparameters.

3) Sharding, merging, and compression.

Large datasets can contain tens or hundreds of thousands of functions. To support scalable preprocessing, the cache manager can shard outputs during processing and optionally merge shards into compressed zip archives for each split (cache_train.zip, cache_validation.zip, cache_test.zip). These zip files are the input consumed by training scripts.

4) Cache signatures and reproducibility.

Each cache dataset is associated with a signature computed from:

- Graph extraction configuration (edge mode, schema version).
- Vocabulary versions and counts (num node types, num edge types).
- Embedding configuration (embedder type, embedding dim).
- Embedding cache fingerprint (path and/or hash of the SQLite embedding cache).
- Feature toggles (use one-hot, use code embeddings, use edge content).

The signature is used to construct a directory path:

<cache_root>/<dataset_name>/<signature>/<split>/cache_<split>.zip

This design ensures that if any input changes (for example, a new embedding cache is generated), the signature changes and a new cache directory is created. This prevents accidental reuse of stale caches and makes experiments reproducible.

III-J. From Preprocessing to Training: Model Inputs and Configuration

While the focus of this section is preprocessing, it is useful to clarify how preprocessing choices map to training configurations.

Training scripts consume:

- cache-dir: root directory containing cache datasets.
- dataset-name: identifier for an embedding + feature configuration (e.g., unixcoder_768d_reveal_full).
- cache-signature: the signature that selects the exact cache version.

The model is configured with:

- input_dim: inferred from the cache (x_dim).
- num_node_types and num_edge_types: derived from vocabularies.
- gnn_type and layers: chosen to match edge-type-aware or call-aware settings.
- pooling and loss functions: chosen based on the experimental objective.

A key point is that preprocessing and training remain synchronized through explicit metadata. The cache summary includes the inferred input dimension and the unique edge type counts observed in the dataset, which reduces configuration errors.

Summary

This methodology section formalizes an end-to-end pipeline for vulnerability detection that is designed to be scalable, reproducible, and robust to dataset and extraction inconsistencies. The pipeline begins with split-aware deduplication and function cleaning, proceeds through per-function file generation and CPG extraction, validates and discovers GraphSON schema properties, builds synchronized vocabularies for node and edge types and content, generates cached embeddings using multiple code embedders, and constructs PyG-ready cache datasets where discrete structural features and dense semantic embeddings are fused by concatenation. By making each stage explicit and by enforcing alignment through hashing and cache signatures, we reduce hidden variability and improve the credibility of experimental comparisons.

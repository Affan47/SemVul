1. PROJECT OVERVIEW
================================================================================

This project implements Graph Neural Network (GNN) based vulnerability detection
using Code Property Graphs (CPGs) generated by Joern. The system transforms
source code into graph representations and uses various GNN architectures to
classify functions as vulnerable or safe.

Key Components:
---------------
- CPG Generation: Joern exports code as GraphSON (nodes + edges)
- Node Features: One-hot node types + code embeddings (Word2Vec/CodeBERT/UniXcoder)
- Edge Types: 18 edge types (AST, CFG, DFG, CALL, etc.)
- GNN Processing: Message passing over graph structure
- Classification: Binary vulnerability prediction

Training Scripts:
-----------------
- train.py        : Basic models (Devign, ImprovedDevign, CallAware, MLP)
- train_advanced.py: Advanced models (RGAT, HGT, MultiView, Hypergraph)
- train_contrastive.py: Contrastive learning with HAGNN

================================================================================

Available via --gnn-type argument in train.py:

+----------------+------------------+--------------------------------------------+
| GNN Type       | Layers Supported | Core Mechanism                             |
+----------------+------------------+--------------------------------------------+
| none           | 0                | Identity (no graph convolution)            |
| ggnn           | 1-6+             | Gated Graph Neural Network (GRU updates)   |
| edge_type      | 1-2              | Edge-type embedding + MLP message passing  |
| edge_type_text | 1-2              | Edge-type + text embedding fusion          |
| gcn            | 1-2              | Graph Convolutional Network                |
| gat            | 1-2              | Graph Attention Network                    |
| call_aware     | 1-4              | CALL-node focused attention                |
+----------------+------------------+--------------------------------------------+

DETAILED MECHANISM DESCRIPTIONS:
--------------------------------

A. GGNN (Gated Graph Neural Network)
   File: models/gnn_layers.py

   Core Formula:
   ┌────────────────────────────────────────────────────────────────┐
   │  m_v = Σ (W_e · h_u)    for all neighbors u with edge type e  │
   │  h_v' = GRU(m_v, h_v)   GRU update with current state         │
   └────────────────────────────────────────────────────────────────┘

   - Uses edge-type-specific weight matrices (W_e)
   - GRU cell maintains input/output dimension equality
   - Unrolled for num_steps iterations (default: 4)
   - LayerNorm after each step for stability

   Best For: Deep networks, reproducing original Devign


B. EdgeTypeGNN
   File: models/gnn_layers.py

   Core Formula:
   ┌────────────────────────────────────────────────────────────────┐
   │  edge_emb = Embedding(edge_type)                               │
   │  msg = MLP([h_source || h_target || edge_emb])                 │
   │  h_v' = MLP([h_v || Aggregate(msg)]) + h_v (residual)         │
   └────────────────────────────────────────────────────────────────┘

   - Edge type embedding layer (more parameter efficient than W_e per type)
   - Two MLPs: message computation and node update
   - Residual connection + LayerNorm

   Best For: Large number of edge types, parameter efficiency


C. EdgeTypeTextGNN
   File: models/gnn_layers.py

   Extension of EdgeTypeGNN:
   - Adds optional edge text embedding projection
   - Fuses edge_type_emb + edge_text_emb before message passing
   - Useful for edges with textual labels

   Best For: When edge content (e.g., variable names) matters


D. CallAwareGNN
   File: models/call_aware.py

   Components:
   ┌────────────────────────────────────────────────────────────────┐
   │  1. CallNodeAttention: Per-node-type importance weights       │
   │     - Learns which node types are important (CALL has highest)│
   │     - Combines with content-based attention                   │
   │                                                               │
   │  2. CALLContextEncoder: Data-flow context around CALL nodes   │
   │     - Encodes incoming data flow (function arguments)         │
   │     - Encodes outgoing data flow (return values)              │
   │                                                               │
   │  3. Full CallAwareGNN: Attention + Context encoding           │
   └────────────────────────────────────────────────────────────────┘

   Key Insight: Vulnerability signal is in WHICH APIs are called

   Best For: API-centric vulnerability detection


E. ShallowGNN (Wrapper)
   File: models/gnn_layers.py

   - Wraps any GNN type for 1-2 layers
   - Prevents over-smoothing problem
   - Automatically selected when gnn_layers <= 2

4. POOLING STRATEGIES
================================================================================

Available via --pooling-type argument:

+---------------+-------------------+--------------------------------------------+
| Pooling Type  | Output Dimension  | Description                                |
+---------------+-------------------+--------------------------------------------+
| mean          | hidden_dim        | Simple global mean pooling                 |
| max           | hidden_dim        | Simple global max pooling                  |
| mean_max      | 2 * hidden_dim    | Concatenate mean and max                   |
| multi_stat    | hidden_dim (proj) | Mean + Max + Std (VECTORIZED, RECOMMENDED) |
| attention     | hidden_dim        | Learnable attention-based pooling          |
| combined      | 3 * hidden_dim    | Multiple strategies fused                  |
| devign        | hidden_dim        | DevignConvHead (original Devign readout)   |
+---------------+-------------------+--------------------------------------------+

MULTI-STAT POOLING (Recommended):
---------------------------------
Uses mathematical identity: Var(X) = E[X²] - E[X]²

┌────────────────────────────────────────────────────────────────────────┐
│  mean = global_mean_pool(x)           # [B, D]                        │
│  sq_mean = global_mean_pool(x²)       # [B, D]                        │
│  var = sq_mean - mean²                # [B, D]                        │
│  std = sqrt(var + eps)                # [B, D]                        │
│  max_val = global_max_pool(x)         # [B, D]                        │
│  output = concat([mean, max_val, std]) # [B, 3*D]                     │
│  output = project(output)             # [B, D] (optional projection)  │
└────────────────────────────────────────────────────────────────────────┘

Benefits:
- Captures distribution shape (not just central tendency)
- Vectorized implementation (very fast)
- Optional projection maintains dimension


DEVIGN CONV HEAD (Original Devign):
-----------------------------------
Compares initial vs final node representations via Conv1D:

┌────────────────────────────────────────────────────────────────────────┐
│  Z = concat(initial_x, final_x, initial_x * final_x, abs(diff))       │
│  Y = final_x                                                           │
│  Path1 = Conv1D(Z) -> BatchNorm -> MaxPool                            │
│  Path2 = Conv1D(Y) -> BatchNorm -> MaxPool                            │
│  output = MLP(concat(Path1, Path2))                                   │
└────────────────────────────────────────────────────────────────────────┘

9.1 RGAT (Relational Graph Attention Network) - RECOMMENDED
------------------------------------------------------------

Memory Efficiency: O(N×R×D) instead of O(E×H×D²)

Architecture:
┌──────────────────────────────────────────────────────────────────────────┐

│    1. Pre-LayerNorm                                                      │
│    2. MemoryEfficientRGATConv:                                           │
│       - Relation-specific W_r (like RGCN)                                │
│       - Edge-type-aware attention (like GATv2)                           │

- Gradient checkpointing for memory efficiency

Architecture: Combines two attention mechanisms

┌──────────────────────────────────────────────────────────────────────────┐
│  Local Attention (GATv2):                                                │
│    - Focuses on immediate neighbors                                      │
│    - Edge-type-aware                                                     │
│                                                                           │
│  Global Attention (Transformer):                                         │
│    - Long-range dependencies                                             │
│    - All-to-all attention                                                │
│                                                                           │
│  Gated Fusion:                                                           │
│    gate = sigmoid(W_gate · [h_local || h_global])                        │
│    h_fused = gate * h_local + (1-gate) * h_global                        │
└──────────────────────────────────────────────────────────────────────────┘

10. KEY INSIGHTS AND RECOMMENDATIONS
================================================================================

FINDING 1: GRAPH STRUCTURE MAY BE NOISY
---------------------------------------
GraphLevelMLP (no GNN) achieves best performance on test sets.
- Aggregate node statistics capture vulnerability patterns
- Graph structure may introduce noise rather than signal
- This suggests the graph topology from Joern may not be perfectly aligned
  with vulnerability semantics

RECOMMENDATION: Start with GraphLevelMLP as baseline, add GNN only if needed


FINDING 2: CALL NODES ARE CRITICAL
----------------------------------
Diagnostic analysis shows vulnerability signal is in CALL nodes.
- Which APIs are called is more predictive than edge types
- Data-flow context around CALL nodes matters
- Edge type distribution is identical in vulnerable vs safe code

RECOMMENDATION: Use CallAwareDevign for API-centric vulnerabilities


FINDING 3: SHALLOW NETWORKS ARE BETTER
--------------------------------------
ImprovedDevign (1-2 layers) outperforms deep GGNN (4+ layers).
- Avoids over-smoothing problem in GNNs
- Structural features help more than multiple GNN layers
- Multi-stat pooling captures more signal than single statistic

RECOMMENDATION: Use 1-2 GNN layers maximum


FINDING 4: EMBEDDINGS MATTER MORE THAN ARCHITECTURE
----------------------------------------------------
Performance ranking: UniXcoder > GraphCodeBERT > CodeT5+ > Word2Vec
- Pre-trained code embeddings capture semantic information
- 768-dimensional embeddings outperform 128-256d

RECOMMENDATION: Use UniXcoder or GraphCodeBERT embeddings


FINDING 5: MEMORY EFFICIENCY IS CRITICAL
----------------------------------------
Large CPGs can have thousands of nodes.
- RGAT uses O(N×R×D) instead of O(E×H×D²)
- Gradient checkpointing reduces memory by trading compute

RECOMMENDATION: Use RGAT with --use-checkpoint for large graphs


RECOMMENDED CONFIGURATION:
-------------------------
For best balance of accuracy and efficiency:

python -m vuln_detection.train \
    --model-type improved_devign \
    --gnn-type ggnn \
    --gnn-layers 2 \
    --hidden-dim 256 \
    --pooling-type multi_stat \
    --use-structural-features \
    --embedder-type word2vec \
    --num-edge-types 18 \
    --dropout 0.2 \
    --batch-size 64 \
    --lr 0.0005

11. GNN FEATURES, BENEFITS, AND MESSAGE PASSING

11.1 WHY GRAPH NEURAL NETWORKS FOR VULNERABILITY DETECTION?
------------------------------------------------------------

Code Property Graphs (CPGs) naturally represent code as graphs:
- Nodes = Code elements (functions, statements, variables, calls)
- Edges = Relationships (AST parent-child, CFG control flow, DFG data flow)

Traditional ML approaches (e.g., bag-of-words, sequence models) lose this
structural information. GNNs preserve and exploit graph topology.

BENEFITS OF GNNS FOR CODE ANALYSIS:
┌──────────────────────────────────────────────────────────────────────────┐
│ 1. STRUCTURAL AWARENESS                                                 │
│    - Captures parent-child relationships (AST)                          │
│    - Captures control flow paths (CFG)                                  │
│    - Captures data dependencies (DFG)                                   │
│    - Understands how code elements interact                             │
│                                                                          │
│ 2. PERMUTATION INVARIANCE                                               │
│    - Order of nodes doesn't matter (unlike sequences)                   │
│    - Same vulnerability detected regardless of code layout              │
│    - Robust to refactoring that doesn't change semantics                │
│                                                                          │
│ 3. INDUCTIVE LEARNING                                                   │
│    - Generalizes to unseen code structures                              │
│    - Learns patterns, not specific code snippets                        │
│    - Works on new functions without retraining                          │
│                                                                          │
│ 4. MULTI-HOP REASONING                                                  │
│    - Information flows across multiple edges                            │
│    - Detects long-range dependencies                                    │
│    - E.g., tainted input flows through multiple functions               │
│                                                                          │
│ 5. HETEROGENEOUS EDGE HANDLING                                          │
│    - Different edge types carry different semantics                     │
│    - AST edges: syntactic structure                                     │
│    - CFG edges: execution order                                         │
│    - DFG edges: value propagation                                       │
└──────────────────────────────────────────────────────────────────────────┘


11.2 MESSAGE PASSING NEURAL NETWORKS (MPNN) FRAMEWORK
------------------------------------------------------

All our GNNs follow the Message Passing Neural Network framework:

GENERAL MPNN FORMULA:
┌──────────────────────────────────────────────────────────────────────────┐
│  For each node v:                                                        │
│                                                                          │
│  1. MESSAGE:    m_v = AGGREGATE({M(h_u, h_v, e_uv) : u ∈ N(v)})         │
│                                                                          │
│  2. UPDATE:     h_v' = UPDATE(h_v, m_v)                                  │
│                                                                          │
│  Where:                                                                  │
│  - h_v     = node v's hidden state                                       │
│  - N(v)    = neighbors of v                                              │
│  - e_uv    = edge features between u and v                               │
│  - M()     = message function                                            │
│  - AGGREGATE = permutation-invariant aggregation (sum, mean, max)        │
│  - UPDATE = update function (GRU, MLP, etc.)                             │
└──────────────────────────────────────────────────────────────────────────┘

WHY MESSAGE PASSING WORKS:
- Each layer aggregates information from 1-hop neighbors
- K layers = K-hop receptive field
- Information diffuses through the graph
- Nodes "learn" about their context


11.3 COMPARISON OF MESSAGE PASSING VARIANTS
--------------------------------------------

┌────────────────┬───────────────────────────────────────────────────────────┐
│ GNN Type       │ Message Function M(h_u, h_v, e_uv)                        │
├────────────────┼───────────────────────────────────────────────────────────┤
│ GGNN           │ W_e · h_u                                                 │
│                │ - Edge-type specific weight matrix W_e                    │
│                │ - Linear transformation per edge type                     │
│                │ - GRU update: h' = GRU(msg, h)                            │
│                │ BENEFIT: Captures edge semantics explicitly               │
├────────────────┼───────────────────────────────────────────────────────────┤
│ EdgeTypeGNN    │ MLP([h_u || h_v || Embed(e)])                             │
│                │ - Learns edge embeddings                                  │
│                │ - MLP combines source, target, edge                       │
│                │ BENEFIT: Parameter efficient, flexible                    │
├────────────────┼───────────────────────────────────────────────────────────┤
│ GCN            │ (1/sqrt(deg_u * deg_v)) · W · h_u                         │
│                │ - Symmetric normalization                                 │
│                │ - Shared weights across edges                             │
│                │ BENEFIT: Simple, fast, proven baseline                    │
├────────────────┼───────────────────────────────────────────────────────────┤
│ GAT            │ α_uv · W · h_u                                            │
│                │ - Attention weights α learned per edge                    │
│                │ - α = softmax(LeakyReLU(a · [Wh_u || Wh_v]))              │
│                │ BENEFIT: Learns importance of neighbors                   │
├────────────────┼───────────────────────────────────────────────────────────┤
│ RGAT           │ Σ_r (α_r · W_r · h_u)                                     │
│                │ - Relation-specific W_r (like RGCN)                       │
│                │ - Attention over relations                                │
│                │ BENEFIT: Best of RGCN + GAT                               │
├────────────────┼───────────────────────────────────────────────────────────┤
│ CallAwareGNN   │ CallAttention(h_u) · ContextEncode(h_u, flow)            │
│                │ - Special attention on CALL nodes                         │
│                │ - Encodes data-flow context                               │
│                │ BENEFIT: Domain-specific for vulnerability                │
└────────────────┴───────────────────────────────────────────────────────────┘


11.4 AGGREGATION FUNCTIONS
--------------------------

Different aggregations capture different properties:

┌──────────────┬────────────────────────────────────────────────────────────┐
│ Aggregation  │ Properties and Use Cases                                  │
├──────────────┼────────────────────────────────────────────────────────────┤
│ SUM          │ - Captures total information from neighbors               │
│              │ - Good for counting (e.g., number of calls)               │
│              │ - Can overflow for high-degree nodes                      │
├──────────────┼────────────────────────────────────────────────────────────┤
│ MEAN         │ - Normalized by neighbor count                            │
│              │ - Good for averaging properties                           │
│              │ - Stable across different graph sizes                     │
├──────────────┼────────────────────────────────────────────────────────────┤
│ MAX          │ - Captures most salient neighbor                          │
│              │ - Good for detecting presence of patterns                 │
│              │ - Ignores redundant information                           │
├──────────────┼────────────────────────────────────────────────────────────┤
│ ATTENTION    │ - Learned importance weights                              │
│              │ - Good when neighbors have varying importance             │
│              │ - More expressive but more parameters                     │
└──────────────┴────────────────────────────────────────────────────────────┘


11.5 WHY THESE SPECIFIC GNN ARCHITECTURES?
------------------------------------------

GGNN (Gated Graph Neural Network):
┌──────────────────────────────────────────────────────────────────────────┐
│ WHY CHOSEN:                                                              │
│ - Original Devign paper used GGNN → fair comparison                      │
│ - GRU updates prevent gradient vanishing in deep networks                │
│ - Edge-type specific weights capture different relation semantics        │
│                                                                          │
│ WHEN TO USE:                                                             │
│ - Deep networks (4+ layers)                                              │
│ - When edge types have distinct semantics                                │
│ - Reproducing Devign baseline                                            │
│                                                                          │
│ MATHEMATICAL PROPERTY:                                                   │
│ - GRU provides selective memory: keeps relevant, forgets irrelevant      │
│ - Update gate: z = σ(W_z · [h, m])                                       │
│ - Reset gate: r = σ(W_r · [h, m])                                        │
│ - New state: h' = (1-z) * h + z * tanh(W · [r*h, m])                     │
└──────────────────────────────────────────────────────────────────────────┘

EdgeTypeGNN:
┌──────────────────────────────────────────────────────────────────────────┐
│ WHY CHOSEN:                                                              │
│ - More parameter efficient than per-type weight matrices                 │
│ - Edge embeddings can be pre-trained or fine-tuned                       │
│ - Residual connections improve gradient flow                             │
│                                                                          │
│ WHEN TO USE:                                                             │
│ - Many edge types (18+ in our case)                                      │
│ - Limited GPU memory                                                     │
│ - Shallow networks (1-2 layers)                                          │
│                                                                          │
│ PARAMETER COMPARISON:                                                    │
│ - GGNN: O(R × D²) for R edge types                                       │
│ - EdgeTypeGNN: O(R × D + D²) - embedding + shared MLP                    │
└──────────────────────────────────────────────────────────────────────────┘

CallAwareGNN:
┌──────────────────────────────────────────────────────────────────────────┐
│ WHY CHOSEN:                                                              │
│ - Diagnostic finding: vulnerability signal is in CALL nodes              │
│ - Edge type distribution identical in vulnerable vs safe code            │
│ - Which APIs called matters more than how they're connected              │
│                                                                          │
│ WHEN TO USE:                                                             │
│ - API-centric vulnerabilities (buffer overflow, format string, etc.)     │
│ - When function calls are primary vulnerability indicators               │
│ - Taint-style vulnerabilities (input → dangerous API)                    │
│                                                                          │
│ KEY INSIGHT:                                                             │
│ - Vulnerable code calls unsafe APIs (gets, strcpy, sprintf, etc.)        │
│ - Safe code calls safe alternatives (fgets, strncpy, snprintf)           │
│ - CALL node content is more discriminative than graph topology           │
└──────────────────────────────────────────────────────────────────────────┘

RGAT (Relational Graph Attention):
┌──────────────────────────────────────────────────────────────────────────┐
│ WHY CHOSEN:                                                              │
│ - Combines RGCN (relation-specific) + GAT (attention)                    │
│ - Memory efficient: O(N×R×D) vs O(E×H×D²)                                │
│ - Handles heterogeneous edge types naturally                             │
│                                                                          │
│ WHEN TO USE:                                                             │
│ - Large graphs (1000+ nodes)                                             │
│ - Memory constrained environments                                        │
│ - Deep networks (4+ layers) with gradient checkpointing                  │
│                                                                          │
│ ATTENTION MECHANISM:                                                     │
│ - Learns which neighbors are important per relation type                 │
│ - Multi-head attention for diverse attention patterns                    │
│ - Scaled dot-product for numerical stability                             │
└──────────────────────────────────────────────────────────────────────────┘


11.6 THE OVER-SMOOTHING PROBLEM
-------------------------------

A critical issue with deep GNNs:

┌──────────────────────────────────────────────────────────────────────────┐
│ PROBLEM:                                                                 │
│ - After many layers, all node representations become similar             │
│ - Information from all nodes mixes together                              │
│ - Distinguishing features are lost                                       │
│                                                                          │
│ MATHEMATICAL EXPLANATION:                                                │
│ - Each layer is a low-pass filter on the graph spectrum                  │
│ - Repeated application smooths high-frequency components                 │
│ - At infinite layers, all nodes converge to same representation          │
│                                                                          │
│ OUR SOLUTION:                                                            │
│ 1. Shallow networks (1-2 layers) - ImprovedDevign                        │
│ 2. Residual connections - preserve original features                     │
│ 3. Layer normalization - prevent representation collapse                 │
│ 4. Multi-stat pooling - capture distribution, not just mean              │
│                                                                          │
│ EVIDENCE:                                                                │
│ - ImprovedDevign (1 layer) outperforms Devign (4 layers)                 │
│ - GraphLevelMLP (0 layers) achieves best performance                     │
│ - Suggests 1-2 hops is sufficient for vulnerability patterns             │
└──────────────────────────────────────────────────────────────────────────┘

12.1 LOSS FUNCTIONS
-------------------

┌──────────────────┬───────────────────────────────────────────────────────┐
│ Loss Type        │ Formula and Use Case                                  │
├──────────────────┼───────────────────────────────────────────────────────┤
│ BCE              │ -[y·log(p) + (1-y)·log(1-p)]                          │
│ (Binary Cross    │ Standard binary classification loss                   │
│  Entropy)        │ Use: balanced datasets                                │
├──────────────────┼───────────────────────────────────────────────────────┤
│ Focal Loss       │ -α·(1-p)^γ·log(p) for hard examples                   │
│                  │ Down-weights easy examples                            │
│                  │ Use: imbalanced datasets, hard example mining         │
│                  │ Default: γ=2, α varies by class                       │
├──────────────────┼───────────────────────────────────────────────────────┤
│ Combined         │ λ·BCE + (1-λ)·Focal                                   │
│                  │ Balances standard and hard-example learning           │
│                  │ Use: when both objectives matter                      │
├──────────────────┼───────────────────────────────────────────────────────┤
│ Contrastive      │ -log[exp(sim(z,z+)/τ) / Σexp(sim(z,z-)/τ)]           │
│ (SCL)            │ Pulls same-class embeddings together                  │
│                  │ Pushes different-class embeddings apart               │
│                  │ Use: train_contrastive.py                             │
└──────────────────┴───────────────────────────────────────────────────────┘
